# 文脈つき並べ替えの知見(imev から)

MeltKelp で zenz の並べ替え(#2)を作るときに、同じ失敗を繰り返さないための記録。
**MeltKelp ではまだ実装していない。** ここに書くのは imev で実際に踏んだことと、それが Meltype の構成で
どう当てはまるか(推測を含むものはそう書く)。実装したら `components/` にページを書き、ここは実装の結果に合わせて直す。

出典: imev の `wiki/components/mozc-context-rerank.md`(2026-10-04〜05)。数値は i5-12600K、CPU、zenz-v3.1-small(Q5_K_M)。
imev の実装は kant0123/imev の `02_src/mozc/context-rerank.patch`(`ContextRerankRewriter::Rewrite()`・`LlmScorer::Impl::Rank()`)。

## 方式の要点

- 候補は Mozc に出させ、LM は**上位の候補(imev は 5 件)の並べ替えだけ**に使う。候補の追加・削除はしない。
- 採点は zenz のプロンプト(文脈 → 読みのカタカナ → 出力)で、文脈 + 読みの共通部分の KV を使い回し、候補ごとに
  系列を分けて 1 回の decode で採点する。採点だけなので 1 回 13〜50ms で済んだ(文脈 56〜60 バイトで 50ms 前後)。
- 実機で並び替わるのを確かめた例: 文脈「劇団の千秋楽の」+ こうえん → 公演、「著名な研究者の」+ こうえん → 講演、
  「街の」+ こうえん → 公園。

## 落とし穴

### かなだけの候補を採点の対象にすると、読みを写したカタカナが勝つ

プロンプトに読みをカタカナで入れるので、LM は読みをそのまま写した「ゲキダン」に高い確率を付ける。対象に入れていたときは、
単独の「げきだん」が「ゲキダン」になった。imev では**表層がひらがな・カタカナだけの候補を対象から外した**。

その代わり、**かなが正解の読みでは漢字の誤候補が先頭のまま動かない**(補助動詞・語尾。読み「したい」で「死体」が先頭のまま、
2 番目にいる「したい」が対象外)。imev #31 で未解決。MeltKelp では、外す・残す・かなだけ別の扱いにする、のどれにするかを
決めてから実装する。

### 元の順位の「事前」が強いと、LM が何を言っても動かない

imev の合成は `-500 × 対数確率 + 300 × 元の順位`(500 は Mozc のコストの単位、300 は Mozc の順位を保つための事前)。
事前は誤った並べ替えを抑えるが、下の「採点の鈍さ」と組み合わさると正しい並べ替えも止める。imev では環境変数で事前を変えられる
ようにしたが、サーバーがサンドボックスで起動されるので変えるのが手間だった。MeltKelp では `Meltype.exe` の設定か
テストから変えられるようにしておくと、事前の効きを切り分けやすい。

Meltype の候補は Mozc と Microsoft IME の候補を並べたもので、Mozc のコストのような共通の尺度が無い。
**元の順位を何で表すか(単純な順位か、エンジンごとの重みか)は MeltKelp で新たに決める必要がある。**

### ユーザーの学習が LM より後に効く(効かせる)

imev では LM の Rewriter をユーザー履歴系の Rewriter の**前**に置いたので、一度確定した候補(テストで繰り返し確定した「記者」など)は
LM が何を言っても先頭に戻った。ユーザーの明示的な選択を優先するための**意図した順序**。

Meltype では学習が 2 か所にある: Mozc ヘルパーの学習(`%LOCALAPPDATA%\Meltype\mozc\`、`HybridConverter.Learn()` で覚える)と、
Meltype 自身の確定履歴・ユーザー辞書(`CompositionController` が候補の並びに反映する)。デコレーターを `HybridConverter` の外に置くと、
Mozc の学習は既に候補順に入った状態で届き、Meltype の確定履歴はデコレーターの後で効く(と見ている。実装時に確かめる)。
**どちらの場合も、学習で先頭に来た候補を LM で下げない。** 動作確認は未学習の語か、学習を消した状態で行う。

### 文脈が空なら採点しない

文脈なしの LM は Mozc 自身の言語モデルと情報が重なるだけで、上のカタカナの誤りを起こす余地だけが残る。

### 文脈の上限は、足し込んだ後に掛ける

imev では文脈を 48 文字に切るのが関数の入口だけで、文節ごとに文脈を追記していくと長文で伸び、採点が KV の上限で失敗していた
(imev PR #12 のレビューで指摘。[[recurring-review-findings]] の「上限・正規化を入口で 1 回だけ掛け、ループ内で育つ値に効いていない」)。

### 実機の C++ の対数確率が PoC より鈍かった(原因は未特定)

同じ入力(文脈「劇団の」・読み「こうえんが」)で、Python の PoC は正解の「公演が」に -0.3、実機の C++ は -7.1。ほかの候補も約 -7 ずれ、
順位の並びも違った。プロンプトは同じなので、llama.cpp の版の差(azooKey の b4846 と公式の新しい版)、トークナイズ、KV の扱いのどれかと
見ていた(imev #33)。鈍いぶん事前に負けやすい。**MeltKelp で C# に移すときは、PoC と同じ入力で対数確率を突き合わせるテストを先に作る。**

### 採点の時間を打ち切る

imev は 1 回の採点を 250ms で打ち切り(`llama_set_abort_callback`)、失敗・打ち切りでは Mozc の順位のまま返した。
モデルの読み込みは別スレッドで行い、終わるまでは採点しない。Meltype では変換が UI スレッドで呼ばれるので、上限はもっと短くする
必要があるかもしれない(`--perf` の p95 / p99 で決める)。

### ライブ変換中の文脈に、組み立て中の文字列が混ざる

imev(Windows の Mozc)はキーごとに変換するので、キー入力中に届く周辺のテキストには組み立て中の変換済みの文字列が含まれ、LM が候補自身を
文脈として見ていた(imev #32)。Meltype で文脈を UI Automation で取るときも、確定前の文字列が入力欄に下線付きで入っている
(Meltype IME)ことがあるので、**文脈は確定済みの部分だけにする**。

## imev の構成に固有で、MeltKelp には当てはまらないこと

- mozc_server は低整合性のサンドボックスで動き、`%LOCALAPPDATA%` の DLL・モデルを読めなかった(`LoadLibrary` がエラー 126)。
  `Meltype.exe` は通常の整合性レベルで動くので、この制約は無い(と見ている)。
- llama.dll は ggml-rpc.dll にも依存し、欠けても 126 でどの DLL かは出なかった。P/Invoke でも同じ形で出るはずなので、
  読み込みに失敗したときは依存 DLL を疑う。
