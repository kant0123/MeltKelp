# 文脈つき並べ替えの知見(imev から)

imev で実際に踏んだことと、MeltKelp の zenz の並べ替え(#2、[[zenz-rerank]])でそれぞれどうしたかの記録。
部品の仕組みと入口は [[zenz-rerank]]、ここは imev との対応と、imev の判断のうち覆したものの理由。

出典: imev の `wiki/components/mozc-context-rerank.md`(2026-10-04〜05)。数値は i5-12600K、CPU、zenz-v3.1-small(Q5_K_M)。
imev の実装は kant0123/imev の `02_src/mozc/context-rerank.patch`(`ContextRerankRewriter::Rewrite()`・`LlmScorer::Impl::Rank()`)。

## 方式の要点

- 候補は Mozc に出させ、LM は**上位の候補(imev は 5 件)の並べ替えだけ**に使う。候補の追加・削除はしない。
- 採点は zenz のプロンプト(文脈 → 読みのカタカナ → 出力)で、文脈 + 読みの共通部分の KV を使い回し、候補ごとに
  系列を分けて 1 回の decode で採点する。採点だけなので 1 回 13〜50ms で済んだ(文脈 56〜60 バイトで 50ms 前後)。
- 実機で並び替わるのを確かめた例: 文脈「劇団の千秋楽の」+ こうえん → 公演、「著名な研究者の」+ こうえん → 講演、
  「街の」+ こうえん → 公園。

## 落とし穴

### かなだけの候補を採点の対象にすると、読みを写したカタカナが勝つ(imev)→ 原因はタグの誤りだった

imev では、LM が読みをそのまま写した「ゲキダン」に高い確率を付け、単独の「げきだん」が「ゲキダン」になったので、
**表層がひらがな・カタカナだけの候補を対象から外した**。その代わり、かなが正解の読みでは漢字の誤候補が先頭のまま動かなかった
(読み「したい」で「死体」が先頭のまま。imev #31)。

**MeltKelp ではかなも採点する。** 写しのカタカナが勝ったのは、imev のプロンプトのタグの誤り(下の「採点の鈍さ」)によるもので、
正しいタグでは文脈つきの写しは低く出る(有名な + げきだん: 劇団 -0.01 / ゲキダン -13.01)。かなが正解の語ではかなが勝つ
(週末に買い物を + したい: したい -0.00 / 死体 -17.28)ので、imev #31 も起きない。数値は [[zenz-rerank]]。

### 元の順位の「事前」が強いと、LM が何を言っても動かない

imev の合成は `-500 × 対数確率 + 300 × 元の順位`(500 は Mozc のコストの単位、300 は Mozc の順位を保つための事前)。
事前は誤った並べ替えを抑えるが、下の「採点の鈍さ」と組み合わさると正しい並べ替えも止める。imev では環境変数で事前を変えられる
ようにしたが、サーバーがサンドボックスで起動されるので変えるのが手間だった。MeltKelp では `Meltype.exe` の設定か
テストから変えられるようにしておくと、事前の効きを切り分けやすい。

Meltype の候補は Mozc と Microsoft IME の候補を並べたもので、Mozc のコストのような共通の尺度が無い。
**MeltKelp では単純な順位にした**(`HybridConverter.Candidates()` の並びの上位 5 件、文節の `Text` が 0 番目)。合成は
「対数確率 − 0.6 × 順位」で、imev と同じ比。調整値は `ZenzRerankOptions` にあり、テストから変えられる。
正しいタグでは正解の候補と次点の差が 3 以上開くことが多く(街の + こうえん: 公園 -0.01 / 講演 -5.35)、事前が正しい並べ替えを
止めることはほぼ無い。差が小さいのは文脈が手がかりにならないとき(それで + はしを: 橋を -1.68 / 箸を -1.97)で、そこは事前で
変換エンジンの順を保つ。

### ユーザーの学習が LM より後に効く(効かせる)

imev では LM の Rewriter をユーザー履歴系の Rewriter の**前**に置いたので、一度確定した候補(テストで繰り返し確定した「記者」など)は
LM が何を言っても先頭に戻った。ユーザーの明示的な選択を優先するための**意図した順序**。

Meltype では学習が 2 か所にある: Mozc ヘルパーの学習(`%LOCALAPPDATA%\Meltype\mozc\`、`HybridConverter.Learn()` で覚える)と、
Meltype 自身の確定履歴・ユーザー辞書(`CompositionController` が候補の並びに反映する)。デコレーターを `HybridConverter` の外に置いたので、
Meltype の確定履歴・ユーザー辞書・文脈の手がかり辞書はデコレーターの後で効く(テストで確かめた)。**Mozc の学習で先頭に来た候補は
見分けられず、LM が下げうる**(Mozc ヘルパーが学習の印を返さないため。[[zenz-rerank]] の「学習との順序」)。
動作確認は未学習の語か、学習を消した状態で行う。

### 文脈が空なら採点しない

文脈なしの LM は Mozc 自身の言語モデルと情報が重なるだけで、上のカタカナの誤りを起こす余地だけが残る。

### 文脈の上限は、足し込んだ後に掛ける

imev では文脈を 48 文字に切るのが関数の入口だけで、文節ごとに文脈を追記していくと長文で伸び、採点が KV の上限で失敗していた
(imev PR #12 のレビューで指摘。[[recurring-review-findings]] の「上限・正規化を入口で 1 回だけ掛け、ループ内で育つ値に効いていない」)。
MeltKelp では採点に渡す直前に末尾 20 文字に切る(`ZenzRerankingConverter.Rerank()`。テスト `Rerank_ContextLimitAppliesAfterAppending`)。

### 実機の C++ の対数確率が PoC より鈍かった → 原因はプロンプトのタグの誤り

同じ入力(文脈「劇団の」・読み「こうえんが」)で、Python の PoC は正解の「公演が」に -0.3、imev の C++ は -7.1 だった(imev #33)。
**原因は imev の `context-rerank.patch` のタグの文字。** zenz のタグは U+EE00(入力)・U+EE01(出力)・U+EE02(文脈)
(azooKey の `ZenzPromptBuilder.swift`)だが、imev は U+E200〜U+E202(UTF-8 の `î` …)を使っていた。
C# に移した直後は同じ鈍さ(劇団の千秋楽の + こうえん: 公演 -7.22)で、タグを直すと -0.03 になった(劇団の + こうえんが: 公演が -0.26。
PoC の -0.3 と合う)。llama.cpp は imev と同じ b4846 のままなので、版の差ではなかった。

### 採点の時間を打ち切る

imev は 1 回の採点を 250ms で打ち切り(`llama_set_abort_callback`)、失敗・打ち切りでは Mozc の順位のまま返した。
モデルの読み込みは別スレッドで行い、終わるまでは採点しない。MeltKelp も同じ形で、上限は 1 回の変換(`ConvertClauses()`)の
採点の合計で 150ms にした(Meltype では変換が UI スレッドで呼ばれ、ライブ変換では打つたびに変換するため)。1 回の採点は 20〜70ms。

### ライブ変換中の文脈に、組み立て中の文字列が混ざる

imev(Windows の Mozc)はキーごとに変換するので、キー入力中に届く周辺のテキストには組み立て中の変換済みの文字列が含まれ、LM が候補自身を
文脈として見ていた(imev #32)。Meltype で文脈を UI Automation で取るときも、確定前の文字列が入力欄に下線付きで入っている
(Meltype IME)ことがあるので、**文脈は確定済みの部分だけにする**。MeltKelp は `_precedingText`(キャレットの前の確定済みの文字)と、
同じ変換の前の文節だけを使う。英単語を挟んだ同じ入力の前の区間は、今は文脈に入らない(#24)。

## imev の構成に固有で、MeltKelp には当てはまらないこと

- mozc_server は低整合性のサンドボックスで動き、`%LOCALAPPDATA%` の DLL・モデルを読めなかった(`LoadLibrary` がエラー 126)。
  `Meltype.exe` は通常の整合性レベルで動くので、この制約は無い(と見ている)。
- llama.dll は ggml-rpc.dll にも依存し、欠けても 126 でどの DLL かは出なかった。P/Invoke でも同じ形で出るはずなので、
  読み込みに失敗したときは依存 DLL を疑う。
