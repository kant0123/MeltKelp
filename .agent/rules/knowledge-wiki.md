# ナレッジ Wiki 運用規約 (`wiki/`)

> `CLAUDE.md` の「ナレッジ Wiki」節の写し。規約を変えるときは `CLAUDE.md` と同じ PR でここも直す。
> ページ規約・frontmatter・log の書式は `wiki-ingest` スキル、健康診断は `wiki-lint` スキル、背景は `docs/wiki_workflow.md`。

プロジェクトの知識は `wiki/` 配下の相互リンクされた Markdown に蓄積する。Wiki は
**常に「今どうなっているか」を表す生きた成果物**で、書くのはエージェント、読むのは人間。
ページは `components/`(何が・どこに)/ `concepts/`(なぜ)/ `operations/`(どう動かす)に置き、
`index.md` がカタログ、`log.md` が追記専用の時系列ログ、`overview.md` が入口。
上流の `docs/`(DEVELOPMENT.md・TSF_DESIGN.md など)は上流の文書なので書き換えず、MeltKelp の知識は `wiki/` に置く。

## 常に守ること

- **コードが正、Wiki が従。** 乖離を見つけたら Wiki を直す(コード側の不具合なら別 Issue)。
  Wiki の記述に合わせるためにコードを変えない。コード・テスト・ログから再導出できる乖離は依頼を待たずに直す。
- **ページ間の散文的な矛盾は勝手に統合しない。** どちらが今の判断か解釈が要るものは両論を残して人間に判定を渡す
  (片方に寄せると消えた側の根拠ごと失われ、推測が記録に昇格する)。
- **書くのはコードを読んでも分からないことだけ。** なぜこの設計か・却下した代替案・事故の経緯・踏むと壊れる前提・
  外部サービスの癖・入口(`path/to/file.cs:123 記号名()`、記号名が主)。
  シグネチャの網羅・構造の写し・コードのコピーは書かない(陳腐化した複製になる)。
- **未実装の構想を置かない。** これから作るものの仕様は Issue 本文、実装した結果は `wiki/`、
  いつ何をしたかは `wiki/log.md` と PR 履歴。
- **着手前に `wiki/index.md` → 関連ページを読む**(コードを grep する前に)。作業途中に hook が `[wiki]` で
  関連ページを示したら、そのファイルを変える判断の前に読む。
- **Wiki の更新は実装と同じ PR に同梱する。** 影響しないと判断した場合も PR 本文にその旨を一行書く。
- **新しいページは実体を書く前に `index.md` の「未作成ページ」節へ名前を予約する。** 残したリンク切れもそこに控える。
  複数セッションが同じ概念を別名で二重に作るのを防ぐため。
- **`index.md` のカタログを手で書き換えない。** 各ページの `summary` から `node scripts/wiki-lint.js --write-index` で生成する。
- **`node scripts/wiki-lint.js` はコミットしてから走らせる**(`updated` を最終コミット日と突き合わせるため)。
- **調査で得た価値ある知見の還元は事前承認済み。** 残す価値があると判断したら聞かずに
  Issue → worktree → PR → マージまで進めてよい。微妙なときは残さない側に倒す。
